## 一、项目概述

### 1.1 项目定位

CToS（采集 → 清洗 → 分析 → 输出）是一套集数据采集、AI 分析、数字员工、知识仓库、即时通讯、智慧舆情于一体的企业级智能系统后端。

### 1.2 技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| 语言 | Python 3.10+ | async/await 异步 |
| 框架 | FastAPI | 高性能异步 Web 框架 |
| ORM | SQLAlchemy 2.0 (async) | 异步 ORM |
| 数据库 | SQLite（开发）/ MySQL（生产） | 通过配置切换 |
| 鉴权 | JWT + Bearer Token | 中间件统一校验 |
| AI | OpenAI API（兼容） | 多 Key、多模型 |

**🔧 2026-05-29 修复：数字员工上下文 bug**

`_trigger_digital_employee_reply()` 函数中构建对话上下文的 SQL 查询存在逻辑缺陷：
- **问题**：外层 WHERE 条件是 `ChatMessage.mentions.like(f'%{worker.user_id}%')`，这要求所有消息的 `mentions` 字段都包含该 worker 的 ID。但数字员工的回复消息的 `mentions` 为 `"[]"`（空数组），永远不满足此条件。导致 LLM 只看到用户问题、看不到自己的回答，误以为所有历史用户问题都是新提问，于是全部重新回答。
- **修复**：改为 `or_` 逻辑：`ChatMessage.sender_id == worker.user_id`（数字员工自己发送的消息）OR `and_(ChatMessage.sender_id != worker.user_id, ChatMessage.mentions.like(...))`（其他用户@该数字员工的消息）

```
                      6. 更新 ExecutionLog status=success, tokens_used=...
```

```
你是一个专业的数据清洗助手。你的任务是分析用户提供的原始采集数据，提取结构化信息。

{
  "title": "提取的文章标题",

  "domain_name": "来源网站域名（去www.前缀）",

要求：
1. title 尽量从 HTML 的 title 标签或首段中提取
2. content 需要去除 script、style 标签和所有 HTML 标签
3. domain_name 从 URL 中提取，需要去掉 "www." 前缀
```

## 十、WebSocket 整合设计（FastAPI 主后端集成方案）

### 10.1 设计变更说明

**2026-05-28 重要更新：** 原独立的 CToSWsChat WebSocket 服务器（端口 8765）已**整合进 FastAPI 主后端**，不再需要单独启动。

| 变更项目 | 旧方案（独立 WS 服务器） | 新方案（整合进主后端） |
|---------|----------------------|-------------------|
| 端口 | 8765（独立） | 8000（与主后端共用） |
| 推送方式 | HTTP 调用 `/internal/push` | 进程内函数调用 `ws_manager.push_to_user()` |
| 鉴权方式 | 内部 API + JWT 验证接口 | 直接调用 `AuthMiddleware.decode_token()` |
| 离线拉取 | HTTP 代理拉取主后端 API | 直接调用 `im_service` 的数据库查询 |
| 部署要求 | 需要启动两个服务 | **只需启动一个服务** |

### 10.2 架构图

```
┌──────────┐   REST API (发送)   ┌──────────────────────────────────┐
│ 客户端 A  │ ─────────────────► │      FastAPI 主后端 (端口 8000)      │
│          │                      │                                  │
│          │ ◄───────────────── │  ┌──────────────┐  ┌────────────┐ │
│          │     HTTP 200       │  │ REST 路由     │  │ ws_manager │ │
└──────────┘                      │  (routers/*)  │  │ (内存单例)  │ │
                                  │              │  │            │ │
┌──────────┐   WebSocket (接收)   │  ┌──────────┐ │  │ 在线映射   │ │
│ 客户端 B  │ ◄───────────────── │  │  ws.py   │ │  │ 推送队列   │ │
│          │  {type:"new_message",│  │ /ws 端点  │◄─┤ 好友缓存   │ │
```

**关键设计原则（不变）：**
- 客户端 **发消息** → 走 REST API
- 客户端 **收消息** → 通过 WebSocket（与主后端同端口）
- WS **只走下行不上行**

### 10.3 核心模块

#### 10.3.1 连接管理器 `services/ws_manager.py`

全局单例 `WSConnectionManager`，管理所有在线 WebSocket 连接。

```python
class WSConnectionManager:
    # 在线用户映射: user_id -> set[WebSocket]
    online_users: dict[int, set[WebSocket]]
    # 反向查找: WebSocket -> user_id
    connection_user: dict[WebSocket, int]

    async def add_connection(ws, user_id, user_info)     # 添加连接
    async def remove_connection(ws) -> user_id           # 移除连接
    async def push_to_user(user_id, event, data) -> dict  # 推送给用户
    async def push_to_group(group_id, exclude_uid, event, data)  # 推送给群组
    def is_user_online(user_id) -> bool                   # 查询在线状态
    async def get_batch_status(user_ids) -> dict          # 批量查询
    async def start_friend_request_polling(user_id)       # 启动好友申请轮询
    async def stop_friend_request_polling(user_id)        # 停止好友申请轮询
```

#### 10.3.2 WebSocket 路由 `routers/ws.py`

| 端点 | 类型 | 说明 |
|------|------|------|
| `GET /ws` | WebSocket | 主 WebSocket 端点：`ws://host:port/ws?token=<JWT>` |
| `POST /api/internal/ws/push` | HTTP | 兼容旧接口：推送消息给用户 |
| `POST /api/internal/ws/push-group` | HTTP | 兼容旧接口：推送消息给群组 |
| `GET /api/internal/ws/user-status` | HTTP | 兼容旧接口：查询用户在线状态 |
| `POST /api/internal/ws/batch-status` | HTTP | 兼容旧接口：批量查询在线状态 |
| `GET /api/ws/stats` | HTTP | 获取 WS 连接统计（在线人数/连接数） |

```
  │ 10. 持续接收推送消息               │
  │ ◄── {type:"new_message",...}     │
  │ ◄── {type:"friend_request",...}  │
```

### 10.5 消息推送流程

以发送私聊消息为例：

```
1. 客户端 POST /api/im/messages
2. im.py 写入 chat_messages 表
3. im.py 调用 ws_push_service.push_to_user(receiver_id, "new_message", data)
   └─► ws_manager.push_to_user() 直接查内存中的 online_users
   └─► 如果用户在线 → WebSocket.send_text() 直接推送
   └─► 如果用户离线 → 返回 delivered=false，等待用户上线后拉取
4. 返回 HTTP 200 给发送方
```

**区别：** 整合前推送需要 3 步（写 DB → HTTP 调 WS 服务 → WS 推送），整合后只需 1 步（写 DB → 直接内存推送）。

### 10.6 好友申请轮询

用户上线后，`ws_manager` 为该用户启动一个后台 asyncio 任务，每 30 秒：
1. 直接调用 `im_service.pull_friend_requests_for_user()` 查询数据库
2. 与本地缓存对比，检测新增/状态变更的申请
3. 有变更时通过 `ws_manager._push_event()` 直接 WebSocket 推送

### 10.7 心跳机制

- 服务器每 30 秒通过 WebSocket 发送 `{"type":"ping","data":{"timestamp":"..."}}`
- 客户端回复 `{"type":"pong"}`
- 如果连接异常断开，`WebSocketDisconnect` 异常触发清理逻辑

### 10.8 现有 REST API 的兼容性

所有现有 REST API **完全保持不变**。前端唯一变化是 WebSocket 连接地址：

```javascript
// 旧（独立 WS 服务器）：
const url = `ws://localhost:8765/ws?token=${token}`;

// 新（整合到主后端）：
const baseUrl = window.location.origin;
const wsBase = baseUrl.replace(/^http/, 'ws');
const url = `${wsBase}/ws?token=${token}`;
```

### 10.11 整合优势总结

| 维度 | 旧方案 | 新方案 |
|------|--------|--------|
| 推送延迟 | ~2-5ms（HTTP 网络开销） | ~0.1ms（内存级调用） |
| 部署复杂度 | 2 个服务 + 健康检查 + 依赖校验 | **1 个服务** |
| 端口占用 | 8000 + 8765 | 仅 8000 |

| 资源消耗 | 额外 asyncio 事件循环 + 2 个进程 | 主进程内完成 |
