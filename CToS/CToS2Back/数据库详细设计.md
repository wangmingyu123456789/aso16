# 数据库详细设计（基于业务需求）

> 数据库反映程序的功能需求，外键一致性是保障业务完整性的关键。
> 本设计基于 `架构分析.md` 和 `Description.txt` 的业务需求，为每张表补充**后端逻辑注释**。
>
> **如何阅读本文档**：
> - 每张表包含：字段定义 → 后端CRUD/查询模式 → 数据流注解
> - 后端开发人员应关注"后端逻辑"和"查询模式"部分，了解代码中如何操作该表

---

## 一、设计原则

| 原则 | 说明 |
|------|------|
| **业务驱动** | 每张表对应一个明确的业务实体，每个字段对应明确的业务属性 |
| **外键一致性** | 所有表间关系通过外键 + 级联策略保证数据完整性 |
| **索引优化** | 对查询频繁的字段建立索引 |
| **类型精确** | 字段类型、长度、是否为空、默认值明确指定 |
| **支持双数据库** | SQLite/MySQL 兼容的字段类型 |

---

## 二、实体关系总览（ER 文字描述）

```
users ──1:N──> user_sessions       # 用户 → 会话（一个用户可以有多个登录会话）
users ──1:1──> workers             # 用户 → 数字员工（一个用户对应一个数字员工配置，通过 workers.user_id 关联，nullable）
users ──1:N──> conversations       # 用户 → 对话列表（一个用户有N个AI对话）
conversations ──1:N──> messages     # 对话 → 消息（一个对话有N条AI消息）
users ──1:N──> friends (双向)       # 用户 → 好友关系（user_id 和 friend_id 都指向 users）
users ──1:N──> group_members        # 用户 → 群成员（一个用户可以加入N个群）
users ──1:N──> chat_messages (发)   # 用户 → 聊天消息（一个用户发送N条消息）
users ──1:N──> token_stats          # 用户 → Token统计（每日统计）
users ──1:N──> system_logs          # 用户 → 操作日志（记录用户操作）
users ──1:N──> files (上传者)       # 用户 → 文件（一个用户上传N个文件）

watch_sources ──1:N──> watch_data          # 瞭望源 → 原始采集数据
watch_data    ──1:N──> warehouse_articles  # 采集数据 → 结构化入库（清洗成功则入库）
watch_data    ──1:N──> cleaning_logs       # 采集数据 → 清洗日志（含执行日志id）

jobs      ──1:N──> workers                   # 工作定义 → 数字员工
workers   ──1:N──> execution_logs            # 数字员工 → 执行记录
execution_logs ──1:N──> execution_messages   # 执行记录 → 多轮消息（支持多轮工具调用）

chat_groups ──1:N──> group_members  # 群组 → 群成员（一个群有N个成员）
chat_groups ──1:N──> chat_messages(receiver_type='group')  # 群组 → 群消息

chat_messages ──N:1──> files (file_id)  # 消息 → 文件（一条消息关联一个文件，SET NULL 级联）

warehouse_articles ──1:N──> sentiment_analyses   # 仓库文章 → 舆情分析（每次分析覆盖一批文章）
sentiment_analyses ──1:N──> sentiment_events      # 舆情分析 → 舆情事件（一次分析提炼多个事件）
sentiment_analyses ──1:N──> sentiment_words       # 舆情分析 → 舆情关键词（词云数据）
sentiment_events    ──1:N──> sentiment_locations  # 舆情事件 → 舆情地点（事件涉及的地理位置）
execution_logs      ──1:1──> sentiment_analyses   # 执行记录 → 舆情分析（舆情分析是一种特殊的 job 工作，在 job 会话中由系统自动输入上下文信息，非用户输入）
```

**后端框架级注解**：所有指向 `users.id` 的外键都设置了 `ON DELETE CASCADE`，意味着：
- 删除用户 → 其所有关联数据自动清理（会话、好友关系、群成员、消息、Token统计、文件）
- 代码中**不需要**手动编写级联删除逻辑，数据库自动处理

## 三、详细表结构

---

### 3.1 用户与权限

---

#### `users` — 用户信息

**业务定位**：整个系统**唯一的用户实体**。三种角色统一存在这张表里，通过 `role` 字段区分：admin（管理员）、user（普通用户）、worker（数字员工，不可登录，password_hash=NULL）。

**后端逻辑**：
- **注册** → INSERT INTO users (username, password_hash, role) VALUES (?, ?, 'user')   # 普通用户注册 role='user'
- **管理员创建用户** → INSERT INTO users (...) VALUES (...) WHERE role IN ('user', 'admin')  # 管理员可创建 admin 和 user
- **创建数字员工** → 事务中：先 INSERT INTO users (username, password_hash=NULL, role='worker') → 获取 users.id → INSERT INTO workers (user_id, job_id, system_prompt, api_key_id, ...)  # 注意：workers.user_id = users.id，一对一
- **登录校验** → SELECT * FROM users WHERE username=? AND password_hash IS NOT NULL AND role IN ('admin', 'user')  # role='worker' 的记录 password_hash=NULL 不可登录
- **获取真实用户列表** → SELECT * FROM users WHERE role IN ('admin', 'user')  # 过滤掉 worker
- **获取数字员工列表** → SELECT * FROM users WHERE role='worker'
- **权限判断** → 读 role 字段 + permissions 字段（细粒度权限）
- **自动填充**：创建数字员工时自动插入 users 记录和 workers 记录在同一事务中

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 用户ID | 所有外键指向此字段；新增时无需传参，DB自动生成 |
| username | VARCHAR(64) | NOT NULL, UNIQUE | 用户名 | 注册/登录的凭证；UNIQUE保证不重名；实际查询时WHERE username=? |
| password_hash | VARCHAR(256) | DEFAULT NULL | 密码哈希 | **真实用户**：用 bcrypt 哈希后存储；**数字员工**：此字段为NULL表示不可密码登录；worker账号必须为NULL |
| nickname | VARCHAR(64) | DEFAULT '' | 用户昵称 | 前端展示用的显示名称；未设置时默认为空字符串，前端回退显示 username |
| role | VARCHAR(16) | NOT NULL, DEFAULT 'user' | **三种角色**: admin/user/worker | admin=管理员；user=普通用户；worker=数字员工（不可登录，password_hash=NULL） |
| permissions | TEXT | DEFAULT '[]' | 权限列表（JSON数组） | **细粒度权限**：如 ["user_management"]；后端用 JSON_EXTRACT 或应用层解析判断 |
| status | VARCHAR(16) | NOT NULL, DEFAULT 'active' | 状态: active/disabled | 禁用用户时更新此字段；查询时 WHERE status='active' 过滤已禁用账号 |
| avatar | VARCHAR(512) | DEFAULT '' | 头像URL | 用户上传头像后的存储路径；显示头像时 SELECT avatar FROM users WHERE id=? |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 后端可直接用 DEFAULT，无需传值；排序时 ORDER BY created_at DESC |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 修改用户信息时 UPDATE users SET updated_at=NOW() |

> **索引**:
> - `idx_users_username` (username) — 登录查询（WHERE username=?）
> - `idx_users_role` (role) — 管理员列表查询（WHERE role='admin'）或筛选数字员工（WHERE role='worker'）
> - `idx_users_status` (status) — 活跃用户筛选（WHERE status='active'）

**角色能力矩阵**：

| 功能区域 | user（普通用户） | admin（管理员） | worker（数字员工） |
|----------|:---:|:---:|:---:|
| 智能问数（Chat） | ✅ | ✅ | ❌（通过workers间接参与） |
| 智能瞭望（Watch） | ✅ | ✅ | ❌ |
| 数字大屏（Dashboard） | ✅ | ✅ | ❌ |
| 数字员工（使用） | ✅ | ✅ | ❌（自身是数字员工） |
| 数据清洗 | ✅ | ✅ | ❌ |
| 数据仓库 | ✅ | ✅ | ❌ |
| 智能聊天（1v1私聊） | ✅ | ✅ | ✅（作为好友角色存在） |
| 智能聊天（群聊） | ✅ | ✅ | ✅（作为群成员存在） |
| 智能聊天（被@回复） | ❌ | ❌ | ✅（数字员工核心功能） |
| 用户管理（管理后台） | ❌ | ✅ | ❌ |
| API Key管理（管理后台） | ❌ | ✅ | ❌ |
| 工作/员工管理（管理后台） | ❌ | ✅ | ❌ |
| 系统配置（管理后台） | ❌ | ✅ | ❌ |
| 群管理（管理后台） | ❌ | ✅ | ❌ |
| 文件管理（管理后台） | ❌ | ✅ | ❌ |
| 聊天服务器管理 | ❌ | ✅ | ❌ |
| 登录系统 | ✅ | ✅ | ❌（password_hash=NULL不可登录） |

**后端鉴权伪代码**：
```python
def check_permission(user_id, required_permission):
    user = db.query("SELECT role, permissions FROM users WHERE id=? AND status='active'", user_id)
    if not user: return False
    # admin 拥有所有权限
    if required_permission in ['user_management', 'system_config'] and user.role != 'admin':
        return False  # 仅 admin 可管理用户
    return True  # 用户侧功能全部开放
```

#### `user_sessions` — 用户会话（JWT Token管理）

**业务定位**：管理用户的登录状态。

**后端逻辑**：
- **登录成功** → INSERT INTO user_sessions (user_id, token, expires_at)
- **每次请求鉴权** → SELECT * FROM user_sessions WHERE token=? AND expires_at > NOW()
- **登出** → DELETE FROM user_sessions WHERE token=?
- **Token过期清理** → 定时任务 DELETE FROM user_sessions WHERE expires_at < NOW()
- **用户删除** → 级联删除所有会话，用户自动登出

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 会话ID | 内部使用，前端不感知 |
| user_id | INTEGER | NOT NULL | → users.id | 用于 JOIN 获取用户信息；鉴权通过后从 session 中读 user_id 用于后续操作 |
| token | VARCHAR(256) | NOT NULL, UNIQUE | JWT Token | 前端通过 Authorization header 传入；每次请求查询此字段 |
| ip_address | VARCHAR(45) | DEFAULT NULL | 登录IP | 记录登录时的客户端IP，用于审计和安全分析 |
| user_agent | VARCHAR(512) | DEFAULT NULL | User-Agent | 记录登录时的浏览器/客户端标识，用于安全分析 |
| expires_at | DATETIME | NOT NULL | 过期时间 | 后端判断：expires_at < NOW() 即过期，返回 401 要求重新登录 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊用途，记录登录时间用于审计 |

> **外键**: `fk_sessions_user` (user_id → users.id ON DELETE CASCADE)
> **索引**:
> - `idx_sessions_token` (token) — 鉴权查询（WHERE token=?）
> - `idx_sessions_user` (user_id) — 查询用户的所有会话（登出全部设备功能）

### 3.2 智能问数（Chat — AI对话）

**数据流总览**：
```
用户发起对话 → conversations 表创建会话 → messages 表逐条追加消息 → API Key调用LLM → 响应写入 messages
                                                                        ↓
                                                                    token_stats 记录消耗
```

---

#### `conversations` — 对话会话

**业务定位**：一个"对话"相当于 ChatGPT 中的一个对话列表条目。每个用户可以有多个对话。

**后端逻辑**：
- **新建对话** → INSERT INTO conversations (user_id, title) VALUES (?, '新会话')
- **获取对话列表** → SELECT * FROM conversations WHERE user_id=? ORDER BY updated_at DESC LIMIT 20 OFFSET ?
- **重命名对话** → UPDATE conversations SET title=? WHERE id=? AND user_id=?
- **删除对话** → DELETE FROM conversations WHERE id=?（级联删除所有消息）
- **获取对话详情** → SELECT * FROM conversations WHERE id=?（用于检查对话是否属于当前用户）

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 会话ID | messages.conversation_id 指向此字段 |
| user_id | INTEGER | NOT NULL | → users.id | **安全问题**：每次操作必须校验 WHERE id=? AND user_id=? 防止越权访问他人对话 |
| title | VARCHAR(128) | DEFAULT '新对话' | 会话标题 | 用户可手动重命名；也支持 AI 自动摘要命名 |
| model_name | VARCHAR(64) | DEFAULT NULL | 使用的模型名称 | 创建对话时记录当前选用的模型，用于后续展示和统计 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊业务用途 |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 对话列表按此字段倒序排列；有新消息时 UPDATE conversations SET updated_at=NOW() |

> **外键**: `fk_conversations_user` (user_id → users.id ON DELETE CASCADE)
> **索引**:
> - `idx_conversations_user` (user_id) — 查询用户对话列表 WHERE user_id=?
> - `idx_conversations_updated` (updated_at) — 排序 ORDER BY updated_at DESC

---

#### `messages` — 对话消息

**业务定位**：AI 对话中的每条消息，包含用户提问和 AI 回复。每个对话会累积 N 条消息。

**后端逻辑**：
- **用户发送消息** → INSERT INTO messages (conversation_id, role='user', content)
- **AI回复** → 流式/非流式写入 messages，role='assistant'
- **获取对话历史** → SELECT * FROM messages WHERE conversation_id=? ORDER BY created_at ASC（发往 LLM 构建上下文）
- **消息上下文截断** → 当消息过多时（如超过 100 条），保留最近的 N 条 + 系统提示，丢弃中间消息
- **删除对话** → 级联删除所有消息（无需单独处理）

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 消息ID | 供前端做唯一标识；删除单条消息 |
| conversation_id | INTEGER | NOT NULL | → conversations.id | **关键外键**：获取对话历史时 JOIN conversations 保证权限 |
| role | VARCHAR(16) | NOT NULL | user/assistant/system | system 是预设的系统提示词（在对话开头插入） |
| content | TEXT | DEFAULT NULL | 消息内容 | 直接发送给 LLM 作为 message content |
| tokens_used | INTEGER | DEFAULT 0 | Token消耗数 | 消耗计入 token_stats；用于计费/限制 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 用于 ORDER BY 排序确保消息顺序正确 |

> **外键**: `fk_messages_conversation` (conversation_id → conversations.id ON DELETE CASCADE)
> **索引**:
> - `idx_messages_conversation` (conversation_id) — 获取对话历史 WHERE conversation_id=?
> - `idx_messages_created` (created_at) — 排序 ORDER BY created_at ASC

**后端构建 LLM 上下文伪代码**：
```python
def build_context(conversation_id, system_prompt):
    messages = db.query("SELECT role, content FROM messages WHERE conversation_id=? ORDER BY created_at ASC", conversation_id)
    context = [{"role": "system", "content": system_prompt}]
    # 截断策略：最多保留最近 30 轮对话
    recent = messages[-60:] if len(messages) > 60 else messages
    context.extend([{"role": m.role, "content": m.content} for m in recent])
    return context
```

### 3.3 智能瞭望（Watch — 数据采集）

**数据流总览**：
```
管理员配置瞭望源(watch_sources) → 定时任务按interval采集 → 原始数据存入watch_data
                                                                  ↓
                                                        AI清洗(cleaning_logs) → 结构化文章(warehouse_articles)
```

---

#### `watch_sources` — 瞭望采集源配置

**业务定位**：配置要采集的目标网站/API 的源信息。每个源对应一个定时任务。

**后端逻辑**：
- **新增瞭望源** → INSERT INTO watch_sources (name, url, interval_seconds, headers, ...)
- **启动采集任务** → 读取所有 enabled=1 的源，为每个源启动一个定时器（由后端调度框架管理）
- **修改采集间隔** → UPDATE watch_sources SET interval_seconds=? WHERE id=?（调度器需重新加载）
- **删除瞭望源** → DELETE FROM watch_sources WHERE id=?（级联删除所有关联的采集数据和清洗结果）
- **获取所有活跃源** → SELECT * FROM watch_sources WHERE enabled=1 ORDER BY interval_seconds ASC

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 源ID | watch_data.source_id 指向此字段 |
| user_id | INTEGER | NOT NULL | → users.id | 瞭望源创建者，用于权限校验 |
| name | VARCHAR(128) | NOT NULL | 采集源名称 | 前端展示用，如 "新浪财经"、"百度热搜" |
| url | VARCHAR(1024) | NOT NULL | 目标URL | GET 请求时直接使用此 URL；POST 时此为 endpoint |
| method | VARCHAR(16) | NOT NULL, DEFAULT 'GET' | 请求方法 | 决定 HTTP 请求方式 |
| headers | TEXT | DEFAULT '{}' | JSON自定义请求头 | 避免 A 账号的 API Key 泄露给 B |
| body_template | TEXT | DEFAULT NULL | 请求体模板 | JSON格式，对应 POST/PUT 的 request body |
| interval_seconds | INTEGER | NOT NULL, DEFAULT 3600 | 采集间隔（秒） | 调度器据此安排采集频率；最小间隔 10 秒限制需在应用层做 |
| enabled | INTEGER | NOT NULL, DEFAULT 1 | 启用: 1/0 | 调度器只读取 enabled=1 的源 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊用途 |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 修改源配置时更新 |

> **索引**:
> - `idx_watchsources_user` (user_id) — 按用户查询瞭望源
> - `idx_watchsources_enabled` (enabled) — 调度器查询 WHERE enabled=1

---

#### `watch_data` — 采集的原始数据

**业务定位**：瞭望源每次采集的原始响应数据。一条采集记录对应一次 HTTP 请求的结果。

**后端逻辑**：
- **采集完成** → INSERT INTO watch_data (source_id, raw_response, parsed_data, status)
- **查询某源的最新采集** → SELECT * FROM watch_data WHERE source_id=? ORDER BY collected_at DESC LIMIT 1
- **查询某源的采集历史** → SELECT * FROM watch_data WHERE source_id=? ORDER BY collected_at DESC LIMIT 20
- **删除瞭望源** → 级联删除所有 watch_data 记录
- **数据存储限制**：raw_response 截断至 10000 字符，超长部分丢弃（防止数据库膨胀过快）

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 数据ID | cleaning_logs.watch_data_id 和 warehouse_articles.watch_data_id 指向此字段 |
| source_id | INTEGER | NOT NULL | → watch_sources.id | 关联对应的瞭望源配置 |
| raw_response | TEXT | DEFAULT NULL | 原始响应（截断10000字符） | 清洗环节从此字段提取数据；LIMIT 10000 在应用层做 |
| parsed_data | TEXT | DEFAULT NULL | 解析后的JSON结构化数据 | 清洗模块可以从此字段读取解析后的结构化数据 |
| status | VARCHAR(16) | NOT NULL, DEFAULT 'success' | 采集状态: success/error | 采集失败时 status='error'，raw_response 存错误信息 |
| error_message | TEXT | DEFAULT NULL | 错误信息 | 采集失败时记录具体错误原因 |
| http_status | INTEGER | DEFAULT NULL | HTTP状态码 | 记录 HTTP 响应状态码，用于排查采集失败原因 |
| collected_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 采集时间 | 用于时间序列分析 |

> **外键**: `fk_watchdata_source` (source_id → watch_sources.id ON DELETE CASCADE)
> **索引**:
> - `idx_watchdata_source` (source_id) — 查询某源的所有采集 WHERE source_id=?
> - `idx_watchdata_status` (status) — 统计成功率/失败率
> - `idx_watchdata_collected` (collected_at) — 按时间范围查询

### 3.4 Token 统计

---

#### `token_stats` — Token消耗统计

**业务定位**：按用户、按日统计 Token 消耗，用于计费、配额限制和数据分析。每条记录对应一个用户一天的某用途 Token 消耗。

**后端逻辑**：
- **记录消耗** → INSERT INTO token_stats (user_id, tokens_used, purpose, model_name, date) VALUES (?, ?, ?, ?, ?)
  - 使用 `INSERT ... ON DUPLICATE KEY UPDATE tokens_used = tokens_used + VALUES(tokens_used)` 的 UPSERT 模式（按 user_id + purpose + date 联合唯一约束合并）
- **查询用户今日消耗** → SELECT SUM(tokens_used) FROM token_stats WHERE user_id=? AND date=CURRENT_DATE
- **查询用户消耗历史** → SELECT date, SUM(tokens_used) FROM token_stats WHERE user_id=? GROUP BY date ORDER BY date DESC LIMIT 30
- **管理员看全局统计** → SELECT date, SUM(tokens_used) FROM token_stats GROUP BY date ORDER BY date DESC

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 统计ID | 仅作为主键使用 |
| user_id | INTEGER | NOT NULL | → users.id | 关联用户，用于查询用户维度的消耗 |
| tokens_used | INTEGER | NOT NULL, DEFAULT 0 | 消耗Token数 | 同一 user_id+purpose+date 的记录应累加 |
| purpose | VARCHAR(32) | NOT NULL, DEFAULT 'chat' | 用途: chat/worker/dataworker/sentiment | 按功能模块统计消耗 |
| model_name | VARCHAR(64) | DEFAULT NULL | 模型名称 | 按模型统计消耗 |
| date | VARCHAR(10) | NOT NULL | 统计日期 YYYY-MM-DD | 代码中用字符串存储，非 DATE 类型 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | - |

> **外键**: `fk_tokenstats_user` (user_id → users.id ON DELETE CASCADE)
> **索引**:
> - `idx_tokenstats_user` (user_id) — 查询某用户的所有消耗记录
> - `idx_tokenstats_date` (date) — 管理员查看全局日统计
> **唯一约束**: `uk_tokenstat_day` (user_id, purpose, date) — 同一用户同一用途同一天只能有一条记录

**后端 UPSERT 伪代码**：
```python
def record_token_usage(user_id, tokens_used, purpose, model_name):
    current_date = datetime.now().strftime("%Y-%m-%d")
    db.execute(
        """INSERT INTO token_stats (user_id, tokens_used, purpose, model_name, date)
           VALUES (?, ?, ?, ?, ?)
           ON DUPLICATE KEY UPDATE tokens_used = tokens_used + VALUES(tokens_used)""",
        user_id, tokens_used, purpose, model_name, current_date
    )
```

### 3.5 数字员工（Digital Workers）

**数据流总览**：
```
管理员定义工作(jobs) → 创建工作关联的工人(workers, 绑定job_id) → 用户派遣工人执行(execution_logs)
```

#### `jobs` — 工作定义

**业务定位**：工作是 AI 可执行任务的抽象定义，**仅定义"工作方法"（工具调用方式），不定义员工人格**。提示词只含"做什么工作"和"如何调用工具"，不含"你是谁"。

**核心设计原则**：
- **jobs与workers解耦**：jobs 只描述"做什么 + 怎么做"，不描述"谁来做"
- **prompt_template 只含工具调用方法**
- **员工人格（你是谁、语气如何）由 workers.system_prompt 定义**
- **最终提示词 = worker.system_prompt + job.prompt_template**，由后端拼接

**后端逻辑**：
- **创建工作** → INSERT INTO jobs (name, description, icon, tool_names, prompt_template) VALUES (?, ?, ?, ?, ?)
- **获取工作列表** → SELECT * FROM jobs ORDER BY sort_order ASC
- **删除工作** → DELETE FROM jobs WHERE id=?（CASCADE：有员工引用的工作不允许删除，外键 RESTRICT）
- **获取工作详情** → SELECT * FROM jobs WHERE id=?（用于编辑时展示）

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 工作ID | **唯一标识**：workers.job_id 指向此字段；用于 JOIN 和程序标识 |
| name | VARCHAR(128) | NOT NULL | 工作名称 | 前端展示 |
| code | VARCHAR(64) | NOT NULL, UNIQUE | 工作唯一编码 | 系统内部标识，如 'data_cleaning'、'sentiment_analysis'，用于预设工作查找和代码引用 |
| description | TEXT | DEFAULT NULL | 工作描述 | 工作卡片上的说明文字 |
| icon | VARCHAR(64) | DEFAULT '🤖' | 图标 | 前端展示 |
| tool_names | TEXT | DEFAULT '[]' | 关联工具名称列表（JSON数组） | 存储工具名称字符串而非ID，如 ["get_weather", "send_email"] |
| prompt_template | TEXT | DEFAULT NULL | **工具调用提示词模板**（含 {tools} 占位符） | **注意**：这里**只包含工具调用的方法提示**，不含"你是谁"的人格描述。人格部分在 workers.system_prompt 中 |
| is_preset | INTEGER | DEFAULT 0 | 是否预设: 1/0 | 预设工作（如 data_cleaning、sentiment_analysis）不可在前端删除 |
| sort_order | INTEGER | DEFAULT 0 | 排序值 | 前端展示顺序 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊用途 |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 修改工作配置时更新 |

> **索引**: `idx_jobs_code` (code), `idx_jobs_sort` (sort_order)

#### `tools` — 注册工具

**业务定位**：工具是数字员工可以调用的外部能力，如"查询天气"、"发送邮件"、"数据库查询"。一个工作可以绑定多个工具。

**后端逻辑**：
- **注册工具** → INSERT INTO tools (name, description, function_schema, module_path, is_builtin) VALUES (?, ?, ?, ?, ?)
- **获取所有工具列表** → GET /api/dispatch/tools 返回所有工具（含 is_builtin 标记）
- **删除工具** → DELETE FROM tools WHERE id=?
- **内置工具不可删除**（is_builtin=1 的工具只能通过代码同步）

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 工具ID | 在 jobs.tool_names 中以名称引用，如 "get_weather" |
| name | VARCHAR(64) | NOT NULL, UNIQUE | 工具名称 | 对应 Python 函数名 |
| description | TEXT | DEFAULT NULL | 工具描述 | 展示给管理员的描述信息 |
| function_schema | TEXT | NOT NULL | JSON Schema格式的函数签名 | **关键字段**：此 schema 被传递给 LLM，让 LLM 知道如何调用此工具 |
| module_path | VARCHAR(256) | DEFAULT NULL | 工具函数模块路径 | 如 `tools.weather.get_weather`，用于动态导入并执行工具函数 |
| is_builtin | INTEGER | DEFAULT 0 | 是否内置: 1/0 | 内置工具（如清洗工具、舆情分析工具）在前端不可删除 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊用途 |

> **索引**: `idx_tools_name` (name)

**function_schema 示例**：

#### `workers` — 数字员工

**业务定位**：数字员工是"工作"的具体实例，**也是直接向聊天业务展现为一个"用户无异"的"人"**。一个工作（如"天气助手"）可以有多个数字员工（如"北京天气助手"和"上海天气助手"）。

**核心设计原则**：
1. **workers.user_id 可为 NULL**：允许存在尚未绑定系统用户的"预留"数字员工配置。但实际投入使用的数字员工必须有对应的 users 记录（role='worker'）
2. **workers 通过 api_key_id 引用 api_keys 表**：大模型配置（base_url、api_key、model 等）统一由 `api_keys` 表管理，workers 仅通过外键 `api_key_id` 关联
3. **workers 的 system_prompt 定义员工人格**
4. **提示词拼接**：`最终提示词 = worker.system_prompt + "\n\n" + job.prompt_template(含工具列表)`，由后端拼接
5. **LLM 调用参数取自 api_keys 表**

**后端逻辑**：
- **创建员工** → 事务中：先 INSERT INTO users (username, password_hash=NULL, role='worker') → 获取 users.id → INSERT INTO workers (user_id, job_id, system_prompt, api_key_id, ...)
- **获取员工列表** → SELECT w.*, u.username, u.avatar FROM workers w LEFT JOIN users u ON w.user_id=u.id ORDER BY w.sort_order ASC
- **禁用员工** → UPDATE workers SET enabled=0 WHERE id=
- **删除员工** → DELETE FROM workers WHERE id=?（CASCADE 删除关联的 users 记录）
- **加载员工执行任务** → SELECT w.*, u.username, u.avatar, j.prompt_template, j.tool_names FROM workers w LEFT JOIN users u ON w.user_id=u.id JOIN jobs j ON w.job_id=j.id WHERE w.id=?

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 员工ID（自增主键） | workers.id 独立自增，通过 workers.user_id 关联 users 表 |
| user_id | INTEGER | DEFAULT NULL, UNIQUE | → users.id（role='worker'） | **关键设计**：外键指向 users.id，可为 NULL（预留员工配置）。实际使用时有值 |
| job_id | INTEGER | NOT NULL | → jobs.id | 此员工所属的工作类型；查询时 JOIN jobs 获取工具列表和提示词模板 |
| name | VARCHAR(128) | NOT NULL | 员工名称 | 前端展示名称 |
| icon | VARCHAR(64) | DEFAULT '🤖' | 图标 | 前端展示 |
| description | TEXT | DEFAULT NULL | 员工描述 | 员工卡片上的说明文字 |
| system_prompt | TEXT | DEFAULT NULL | **人格提示词——定义员工的"性格"** | **核心字段**："你是川农小助手，对川农的消息很了解，身份是学长。" |
| api_key_id | INTEGER | DEFAULT NULL | → api_keys.id（大模型配置引用） | 外键引用 api_keys 表统一管理；可为 NULL（使用系统默认 Key） |
| enabled | INTEGER | NOT NULL, DEFAULT 1 | 启用: 1/0 | 调度器/用户前端只显示 enabled=1 的员工 |
| is_preset | INTEGER | DEFAULT 0 | 是否预设: 1/0 | 预设员工在前端不可删除 |
| sort_order | INTEGER | DEFAULT 0 | 排序值 | 前端展示顺序 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 无特殊用途 |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 修改员工配置时更新 |

> **外键**:
> - `fk_workers_user` (user_id → users.id ON DELETE CASCADE) — **删除 worker 时同时删除对应的 users 记录**
> - `fk_workers_job` (job_id → jobs.id ON DELETE CASCADE) — **删工作定义 → 自动删关联员工**
> - `fk_workers_apikey` (api_key_id → api_keys.id ON DELETE RESTRICT) — **RESTRICT：不允许删除被员工引用的 API Key**
> **索引**: `idx_workers_user` (user_id), `idx_workers_job` (job_id), `idx_workers_enabled` (enabled), `idx_workers_sort` (sort_order)

**创建员工的事务伪代码（workers.user_id = users.id 一对一关联）**：
```python
def create_worker(name, job_id, system_prompt, api_key_id, avatar_url=None):
    with db.transaction():
        # Step 1: 先插入 users 表，获取 user_id
        user_id = db.insert(
            "INSERT INTO users (username, password_hash, role, status, avatar) VALUES (?, NULL, 'worker', 'active', ?)",
            name, avatar_url
        )
        # Step 2: 插入 workers 表，user_id 指向 users.id（workers.id 自增，独立于 users.id）
        worker_id = db.insert(
            """INSERT INTO workers (user_id, job_id, name, icon, system_prompt, api_key_id)
               VALUES (?, ?, ?, ?, ?, ?)""",
            user_id, job_id, name, "🤖", system_prompt, api_key_id
        )
    return worker_id
```

#### `execution_logs` — 执行记录

**业务定位**：记录数字员工（包括清洗 worker）每次执行的任务详情。多轮工具调用过程的每一条消息存储于 `execution_messages` 表，而本表只保留头部的汇总信息和最终结果。

**核心设计原则**：
1. **execution_logs 作为头部汇总**
2. **execution_messages 作为详细日志**
3. **数据清洗共享此表**：通过 `execution_logs.cleaning_log_id` 正向关联 cleaning_logs
4. **舆情分析共享此表**：通过 `execution_logs.sentiment_analysis_id` 关联 sentiment_analyses

**后端逻辑**：
- **用户派遣员工** → INSERT INTO execution_logs (worker_id, user_query) VALUES (?, ?)
- **启动清洗任务** → INSERT INTO execution_logs (worker_id=清洗员工ID, user_query=?, cleaning_log_id=?) VALUES (...)
- **启动舆情分析** → INSERT INTO execution_logs (worker_id=舆情员工ID, user_query=?, sentiment_analysis_id=?) VALUES (...)
- **执行完成** → UPDATE execution_logs SET final_response=?, status=?, tokens_used=? WHERE id=?
- **查询执行历史** → SELECT * FROM execution_logs WHERE worker_id=? ORDER BY created_at DESC LIMIT 20

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 执行ID | 供前端追踪单次执行的状态 |
| worker_id | INTEGER | NOT NULL | → workers.id | 关联被执行的数字员工 |
| cleaning_log_id | INTEGER | DEFAULT NULL, UNIQUE | → cleaning_logs.id | **清洗任务专属**：UNIQUE 约束保证每条清洗记录只对应一条执行记录 |
| sentiment_analysis_id | INTEGER | DEFAULT NULL | → sentiment_analyses.id | **舆情分析任务专属**：⚠️ **无 UNIQUE 约束**（一条舆情分析可能多次执行） |
| user_query | TEXT | DEFAULT NULL | 用户查询内容 | 用户在输入框中输入的问题 |
| final_response | TEXT | DEFAULT NULL | 最终回复 | 给用户的最终答案 |
| status | VARCHAR(16) | NOT NULL, DEFAULT 'processing' | 状态: processing/success/error | 执行过程中出错时 status='error' |
| tokens_used | INTEGER | DEFAULT 0 | Token消耗 | 计入 token_stats 用于日统计 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 用于查询历史记录排序 |
| updated_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 更新时间 | 执行状态变更时更新 |

> **外键**:
> - `fk_executionlogs_worker` (worker_id → workers.id ON DELETE CASCADE)
> - `fk_executionlogs_cleaninglog` (cleaning_log_id → cleaning_logs.id ON DELETE CASCADE)
> - `fk_executionlogs_sentimentanalysis` (sentiment_analysis_id → sentiment_analyses.id ON DELETE CASCADE)
> **索引**:
> - `idx_executionlogs_worker` (worker_id) — 查询某员工的历史执行记录
> - `idx_executionlogs_status` (status) — 按状态筛选执行记录
> - `idx_executionlogs_created` (created_at) — 按时间查询

#### `execution_messages` — 执行消息（多轮工具调用日志）

**业务定位**：记录数字员工（包括清洗 worker）在一次执行过程中产生的所有消息。支持 system / user / assistant / tool 四种角色，完整记录 LLM 多轮工具调用的所有交互。

**后端逻辑**：
- **执行开始（记录系统提示词）** → INSERT INTO execution_messages (execution_log_id, role='system', content=system_prompt)
- **用户查询/工具结果回传** → INSERT INTO execution_messages (execution_log_id, role='user', content)
- **LLM 回复（含 tool_calls）** → INSERT INTO execution_messages (execution_log_id, role='assistant', content, tool_calls_json)
- **工具执行结果** → INSERT INTO execution_messages (execution_log_id, role='tool', content, tool_call_id)
- **获取执行消息历史** → SELECT * FROM execution_messages WHERE execution_log_id=? ORDER BY created_at ASC

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 消息ID | 供前端/日志追踪 |
| execution_log_id | INTEGER | NOT NULL | → execution_logs.id | **关键外键**：关联到具体的执行记录 |
| role | VARCHAR(16) | NOT NULL | system/user/assistant/tool | system: 系统提示词；user: 用户输入/工具结果反馈；assistant: LLM回复；tool: 工具执行结果 |
| content | TEXT | DEFAULT NULL | 消息内容 | assistant 的回复内容或 tool 的执行结果 |
| tool_call_id | VARCHAR(64) | DEFAULT NULL | 工具调用ID | role='tool' 时必填，关联 assistant 消息中的 tool_calls[x].id |
| tool_calls_json | TEXT | DEFAULT NULL | JSON工具调用列表 | role='assistant' 时 LLM 返回的 tool_calls 参数 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 用于 ORDER BY 排序确保消息顺序正确 |

> **外键**: `fk_executionmsgs_log` (execution_log_id → execution_logs.id ON DELETE CASCADE)
> **索引**:
> - `idx_executionmsgs_log` (execution_log_id) — 获取某次执行的所有消息 WHERE execution_log_id=?

### 3.8 智能聊天（仿微信即时通讯）

**数据流总览**：
```
添加好友(friends)   → 一对一私聊(chat_messages, receiver_type='user')
创建群(chat_groups)  → 加群成员(group_members) → 群聊(chat_messages, receiver_type='group')
                                                        ↓
                                                   文件/图片上传(files) → 关联消息
```

**核心设计理念**：`chat_messages` 表通过 `receiver_type` 字段区分私聊和群聊。

---

#### `friends` — 好友关系

**业务定位**：用户之间的好友关系，支持双向好友关系。通过 `is_blocked` 字段管理拉黑状态。

**后端逻辑**：
- **发送好友请求** → INSERT INTO friend_requests (sender_id, receiver_id, message)
- **接受好友请求** → INSERT INTO friends (user_id, friend_id) VALUES (?, ?) 和 (?, ?)（双向插入）
- **删除好友** → DELETE FROM friends WHERE (user_id=? AND friend_id=?) OR (user_id=? AND friend_id=?)

| 字段 | 类型 | 约束 | 说明 | 后端逻辑注解 |
|------|------|------|------|------------|
| id | INTEGER | PK, AUTO_INCREMENT | 关系ID | 无特殊用途 |
| user_id | INTEGER | NOT NULL | → users.id（本人） | 发起方的用户ID |
| friend_id | INTEGER | NOT NULL | → users.id（好友） | 接收方的用户ID |
| remark | VARCHAR(64) | DEFAULT NULL | 备注名 | 用户给好友设置的备注名称 |
| is_blocked | INTEGER | DEFAULT 0 | 是否拉黑: 1/0 | 拉黑后不再接收对方消息 |
| created_at | DATETIME | NOT NULL, CURRENT_TIMESTAMP | 创建时间 | 用于按时间排序好友列表 |

> **外键**:
> - `fk_friends_user` (user_id → users.id ON DELETE CASCADE)
> - `fk_friends_friend` (friend_id → users.id ON DELETE CASCADE)
> **唯一约束**: `uk_friendship` (user_id, friend_id) — 不能重复添加好友
> **索引**:
> - `idx_friends_user` (user_id) — 查询某用户的好友关系
> - `idx_friends_friend` (friend_id) — 查询"谁加我为好友"
